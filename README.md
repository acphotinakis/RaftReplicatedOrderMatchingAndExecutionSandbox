# Project Overview & Research Context

## 1. High-Level Project Objective

* **Problem Statement:** Consensus can make replicas agree on a committed command sequence, but agreement alone does not establish that a trading application will preserve identical observable state across replicas. This project investigates the end-to-end gap between Raft log agreement and deterministic, effectively-once execution of simulated market events and orders: every replica must derive the same order book, fills, cash, positions, order status, and client result despite leader failure, message faults, retries, restart, and log repair. It must also separate the costs of matching, serialization, persistence, replication, failover, and recovery rather than treating consensus as cost-free.
* **Our Working Hypothesis / Proposed Solution:** **Working hypothesis placeholder:** a fixed three-node Raft cluster, coupled to a pure deterministic matching and portfolio state machine and replicated client-request deduplication, will preserve identical state at every common applied log index under the stated crash-recovery model. We will test this using a shared pure protocol/application core, a seeded discrete-event fault simulator, a crash-consistent write-ahead log (WAL), canonical state digests, a small TLA+/PlusCal model, and a real Tokio/Tonic three-process deployment.
* **Core Scope & Boundaries:**
  + **In scope:** stable Rust 2024; exactly three nodes with fixed membership; leader election, heartbeats,    `RequestVote`,    `AppendEntries`, majority commit, conflict repair, ordered apply, crash/restart recovery, durable hard state and log entries; a bounded CSV or JSON Lines trace; one instrument; limit orders with price-time priority; integer price ticks and quantity lots; minimal cash/position/reservation accounting; stable client IDs and request sequences; deterministic replay; failpoints, partitions, delay/drop/duplicate/reorder faults; canonical component digests; WAL checksums and partial-tail recovery; property tests, fuzzing, selected Loom checks, TLA+/TLC model checking, and controlled performance experiments.
  + **Deferred until the correctness baseline works:** cancellation beyond stable submission, snapshots and installation, order-storage or channel optimizations, alternative encodings, core pinning,    `io_uring`, memory-mapped logging, and comparison against `raft-rs` or OpenRaft.
  + **Out of scope:** Byzantine fault tolerance; dynamic membership, joint consensus, learners, Multi-Raft, distributed matching shards, leader leases, pre-vote, leadership transfer, and optimized reads; real brokerage/exchange connectivity; production-HFT latency claims; floating point in replicated transitions; margin, short selling, derivatives, fees, and a broad order-type catalog; TLS/PKI, authentication, authorization, geo-replication, Kafka, Kubernetes, DPDK, RDMA, FPGA implementation, and a web dashboard. The project targets effectively-once logical execution through replicated idempotency, not exactly-once message delivery.

## 4. Unified Terminology & Notation Glossary

* **Replicated state machine (RSM):** A set of replicas that begin from equivalent state and execute the same deterministic commands in the same order. In this project, Raft orders commands and the matching/portfolio application is the replicated state machine.
* **Consensus:** Agreement among non-Byzantine nodes on a durable ordered log despite crashes and communication faults. Consensus does not by itself make nondeterministic application code deterministic.
* **Server / node / replica:** One member of the fixed three-node Raft cluster. Use **node** in project prose; use a paper's original term when discussing its algorithm.
* **Leader / primary / coordinator / distinguished proposer:** The node currently responsible for accepting client commands and driving replication. These names are related across Raft/Paxos literature; this project standardizes on **leader**.
* **Follower:** A passive Raft role that responds to leader and candidate RPCs and may start an election after its election timeout.
* **Candidate:** A temporary Raft role attempting to become leader by incrementing its term, voting for itself, and requesting votes.
* **Term / view / ballot / proposal number / round:** A totally ordered leadership epoch. This project uses Raft's integer `term`; larger terms supersede smaller ones.
* **`current_term`:** Highest term a node has observed. It is durable hard state and monotonically nondecreasing.
* **`voted_for`:** Candidate receiving a node's vote in `current_term`, or none. It is durable hard state.
* **`RequestVote`:** Raft election RPC. Paxos literature may describe analogous phase-1 messages as prepare/promise or phase1a/phase1b.
* **`AppendEntries`:** Raft RPC used for both log replication and empty heartbeats. Paxos literature may describe analogous phase-2 messages as accept/propose and accepted or phase2a/phase2b. A heartbeat is not exempt from the normal consistency checks.
* **Heartbeat:** An `AppendEntries` RPC carrying no new entries, used to maintain leadership and convey commit progress. It remains a full `AppendEntries` consistency operation.
* **Election timeout:** Randomized period after which an eligible follower or candidate begins a new election if it has neither received valid leader communication nor granted a vote under Raft's rules. Timing affects liveness, not safety.
* **Log entry:** A project command plus Raft metadata, principally `term` and `index`. Commands include state-changing market events and order requests.
* **Log index (`index`,    `i`):** One-based logical position of an entry in the Raft log. It is not a vector offset and may differ from an in-memory array position after snapshotting.
* **Log Matching Property:** If two logs contain entries with the same index and term, the logs are identical through that index.
* **Up-to-date log:** Voting comparison based first on the last entry's term and then on its index. Length alone is insufficient.
* **`next_index[peer]`:** Leader's next candidate log index to send to a peer.
* **`match_index[peer]`:** Highest log index known replicated on a peer.
* **Conflict repair:** Rejection and backtracking process that finds a matching prefix and removes only a genuinely conflicting suffix. Followers must not truncate merely because an `AppendEntries` message is empty or stale.
* **Quorum / majority:** Any two nodes in this fixed three-node cluster. Intersecting majorities prevent two conflicting committed histories under the crash-fault assumptions.
* **Committed entry / `commit_index`:** An entry known safe under Raft's commitment rule;  `commit_index` is the highest such index known locally. A leader directly advances commitment by counting replicas only for entries from its current term; earlier entries become committed indirectly.
* **Applied entry / `last_applied`:** A committed entry already executed by the application state machine;  `last_applied` is the highest applied index. Written, synchronized, replicated, committed, applied, and acknowledged are distinct states.
* **Leader Completeness Property:** If an entry is committed in a term, every leader elected in a later term contains that entry.
* **State-machine safety:** No two nodes apply different commands at the same log index.
* **Safety:** Nothing invalid happens: conflicting commands are not committed/applied at the same logical position, acknowledged commands are not lost under the persistence contract, and one logical request does not create multiple logical effects.
* **Liveness / availability:** A stable communicating majority eventually elects a leader and resumes commitment. Raft does not promise progress without a majority or under indefinitely adverse timing.
* **Crash-stop / crash-recovery:** In crash-stop, a failed node does not return. This project emphasizes crash-recovery: a node may restart from durable hard state, WAL entries, and eventually a snapshot, then catch up.
* **Fail-stop vs. Byzantine:** Fail-stop/crash faults halt or disconnect nodes without malicious arbitrary behavior. Byzantine faults may produce arbitrary or adversarial behavior and are out of scope.
* **WAL (write-ahead log):** Project-owned append-only durable record stream with framing, schema version, term, index, payload, and CRC32C. Recovery must address short writes, interruptions, checksum failures, and incomplete trailing records.
* **Snapshot / `last_included_index` / `last_included_term`:** Compacted application state plus the last represented Raft position. Snapshot installation and log-prefix disposal must be coordinated so restart cannot reapply already included entries.
* **Command:** Every input that may change replicated state. If a trade or quote affects matching, it must be a committed `MarketEvent`, not independently consumed local data.
* **Deterministic transition / `apply`:** Pure function `(previous_state, committed_command) -> (new_state, deterministic_events)`. It may not depend on wall time, randomness, floating point, locale, node identity, pointer values, unordered iteration, network I/O, disk I/O, or asynchronous scheduling.
* **Price-time priority:** Orders at better prices execute first; orders at the same price execute in authoritative committed order. This project uses log index plus an intra-entry ordinal as logical time.
* **Canonical digest:** Hash of explicitly encoded, deterministically ordered logical fields. Separate digests cover committed commands, orders, fills, portfolios, and deduplication state; raw memory, padding, addresses, and incidental map order are forbidden inputs.
* **Idempotency key:** Stable pair `(client_id, request_sequence)` identifying one logical request across retries.
* **Replicated deduplication:** Application state mapping an idempotency key to its original outcome so a retry returns the prior result without applying the command twice.
* **Effectively-once logical execution:** At-least-once request transport plus replicated deduplication produces one application effect per logical request under documented crash-recovery assumptions. This is not exactly-once delivery.
* **Linearizable write:** A completed committed write appears to take effect atomically between invocation and response. A crash after commit but before response leaves the client uncertain, which requires retry plus deduplication.
* **Deterministic simulator:** Seeded discrete-event environment with virtual monotonic time, stable tie-breaking, simulated network/storage/process lifecycle, and replayable fault history; it executes the same pure Raft and application cores as production adapters.
* **Failpoint:** Named injection boundary around append, synchronization, truncation, snapshot replacement, apply, or client response used to reproduce crash windows.
* **Model checking:** Exhaustive exploration of a bounded formal TLA+/PlusCal model by TLC. It validates modeled invariants but does not prove the Rust implementation correct.
* **Open-loop load:** Work arrives according to an external schedule rather than waiting for each response, exposing queueing and saturation instead of hiding overload through coordinated omission.
* **Tail latency:** High-percentile response time (`p95`,    `p99`,    `p99.9`, maximum), reported with throughput, workload, WAL policy, network conditions, and environment metadata.
* **HTAP / OLTP / OLAP:** Hybrid transactional and analytical processing; online transaction processing; online analytical processing. TiDB uses different Raft-fed physical replicas to isolate OLTP and OLAP, but this project's order-matching state machine is not an HTAP database.
* **Learner:** TiDB's non-voting asynchronous Raft replica used to build a columnar analytical copy. Learners do not participate in this project's fixed three-voter MVP.
* **Region / Multi-Raft:** TiDB partitions data into Regions, each managed by a Raft group. This project uses one fixed Raft group and no data sharding.

## 5. Primary Research Questions & Evaluation Criteria

* **Q1: Does Raft agreement produce identical trading state, not merely identical logs?** At every common `last_applied`, all live or recovered replicas must have the same committed prefix and identical canonical digests for orders, fills, portfolios, and deduplication results. Check after every applied command in golden, generated, and faulted histories.
* **Q2: Which sources of nondeterminism can cause divergence despite a common committed prefix?** Exercise ordered-collection behavior, price-time tie breaking, integer arithmetic and overflow, market-event ordering, stable identifiers, serialization, and replay. The criterion is zero digest divergence for identical prefixes and deterministic reproduction of any failing seed.
* **Q3: Are safety and effectively-once semantics preserved at every leader-failure boundary?** Inject failure before local append, after local append but before majority replication, after majority commit but before response, during suffix repair, and around apply/persistence. No acknowledged command may be lost, no uncommitted command may be treated as committed, and retry must not duplicate a logical order or fill.
* **Q4: Can crashed or partitioned replicas recover without violating Raft's log and application invariants?** Test stale-term traffic, asymmetric partitions, divergent uncommitted suffixes, follower restart/catch-up, partial WAL tails, checksum failures, and eventually interrupted snapshot installation. Require monotonic term/commit/apply state, correct prefix repair, identical state at common applied indexes, and eventual convergence after a stable majority and healthy storage return.
* **Q5: Under what timing and fault assumptions does the cluster regain liveness?** Vary election-timeout ranges, message delay/drop/reorder/duplication, repeated elections, and leader isolation. A stable majority must eventually elect one leader for a term and resume commits; minority partitions must not commit independently. Report election/failover interruption distributions rather than only averages.
* **Q6: What are the incremental costs of deterministic execution, durability, and consensus?** Compare pure matching, single-node WAL-backed matching, three-node memory-only Raft, and three-node durable Raft using the same workload. Report throughput/saturation, p50/p95/p99/p99.9/max latency, allocations, serialization/copying, WAL synchronization, replication lag, failover interruption, replay/catch-up time, and relevant Linux hardware counters with seeds and complete environment metadata.

## 6. Synthesis & Known Open Challenges

* **Agreement is necessary but not sufficient.** Schneider's RSM model and the Raft sources jointly require deterministic commands, common ordering, and controlled outputs. The project must place every state-changing market input in the log and remove wall time, random iteration, floating point, and asynchronous side effects from `apply()`.
* **The rare paths define correctness.** Ongaro/Ousterhout and Gjengset repeatedly expose failures in higher-term handling, election-timer reset conditions, empty `AppendEntries`, suffix truncation, current-term commitment, stale replies, snapshot indexes, and application ordering. Happy-path replication is not meaningful evidence without the required adversarial matrix.
* **Client ambiguity crosses the consensus/application boundary.** A leader can commit and then fail before responding. Linearizable commitment does not eliminate this ambiguity; stable request IDs and replicated results are required to prevent duplicate orders and fills.
* **Persistence semantics must match protocol acknowledgments.** Correctness depends on durably recording `current_term`, `voted_for`, and log entries before sending responses that rely on them. Written, synchronized, replicated, committed, applied, and client-acknowledged must remain separate states, especially under partial writes and restart.
* **Snapshots couple protocol indexes to application state.** Compaction must include application state, deduplication state,    `last_included_index`, and `last_included_term`. Atomic replacement, interrupted installation, and prefix deletion create recovery windows that should remain deferred until plain WAL replay is correct.
* **Safety and liveness rely on different assumptions.** Raft safety must not depend on synchronized clocks; liveness depends on a sufficiently stable communicating majority and suitable timeout separation. Partitions and stale leaders must halt unsafe progress even when that reduces availability.
* **The leader and durable quorum are performance bottlenecks.** Raft centralizes sequencing, while WAL synchronization and majority round trips add latency. Batching and pipelining can improve throughput but enlarge queues, complicate failure boundaries, and potentially worsen tail latency; they must be measured after establishing a correct baseline.
* **Benchmark design can conceal overload.** Closed-loop clients, averages, undocumented CPU settings, and discarded outliers can misrepresent performance. The project therefore calls for open-loop load, HDR distributions, saturation reporting, warm-up and repeated runs, confidence intervals, raw data, and full hardware/software metadata.
* **Formal models, simulation, and real processes cover different failure surfaces.** TLA+/TLC checks the bounded protocol model; the deterministic simulator explores replayable distributed histories; fuzzing targets parsers and WAL recovery; Loom addresses small shared-memory adapters; real processes expose OS, file, scheduler, and network behavior. No single method substitutes for the others or proves the implementation correct.
* **Production prior art must be scaled down deliberately.** TiDB validates the architectural power of Raft-fed state transformations but introduces learners, Multi-Raft, SQL transactions, Regions, and HTAP concerns. Importing those mechanisms would obscure the project's primary question rather than strengthen it.
* **Raft versus Paxos is not the project question.** Howard and Mortier show substantial common structure and locate a major difference in leader election and log preparation. Paxos remains useful comparative context, but the assessed artifact should implement and test the restricted Raft contract rather than attempt a broad consensus-family comparison.
* **Scope pressure is an unresolved delivery risk.** A pure matcher, restricted Raft, deterministic simulator, WAL/recovery layer, production adapter, formal model, fault campaign, and performance study already constitute a large semester project. Snapshots, cancellation, deep low-latency optimizations, and comparison implementations should be cut before any core safety or reproducibility evidence is weakened.
